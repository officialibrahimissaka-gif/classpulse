No plaintext secret is a template parameter, source file or image layer. Runtime secret JSON keys: `DATABASE_URL`, `REDIS_URL`, `SESSION_KEY`, `DATA_KEY`. Keys must be 32 random bytes hex-encoded, separately generated per environment, stored through Secrets Manager by a controlled operator. Dispatcher secret contains only its directory URL; migration secret contains only a dedicated owner URL. Encryption for external Secrets Manager secrets must use the reviewed key policy accessible to the narrow execution role; adjust scoped key references after actual key selection. Billing/retention credentials are separate one-off workloads and absent from web/worker task definitions. No automatic master-password propagation into runtime credentials occurs.

## Sequence: dark staging before production

1. Create accounts, accountable owners, spend alerts, repository access and protected `staging`/`production` GitHub environments. Restrict OIDC trust to `repo:officialibrahimissaka-gif/classpulse:environment:<environment>` and audience `sts.amazonaws.com`; attach a reviewed least-privilege deploy policy, narrow `iam:PassRole`, and account fences. The workflow does not create or enforce GitHub protection settings by itself.
2. Verify region/service/engine/instance support, service quotas, acceptable provider/transfer terms, budgets and DNS authority. Lint both templates: `cfn-lint infra/aws/network.template.json infra/aws/cell.template.json` (tested with 1.47.1). Obtain a CloudFormation change-set/cost/IAM review. Lint is not an AWS account plan or security certification.
3. Provision the network in a synthetic-only staging account under the normal change process. Provision an initial dark cell with `ReleaseTraffic=false`, supported `PostgresEngineVersion`, image digests, owned Route53 zone/subdomain, SES mail domain, notification recipient and secret ARNs. This initial foundation bootstrap precedes full release evidence and is a separately reviewed infrastructure operation; the release workflow deliberately refuses to bypass missing production gates.
4. Publish all three SES DKIM CNAME pairs from the identity resource; verify sender ownership and required production sending access in the actual region. Configure reviewed SPF/DMARC, bounce/complaint handling and staging destination allowlist. SES identity creation does not establish delivery or remove sandbox restrictions.
5. Build once from the tested source commit; scan dependencies/images, generate SBOM/provenance, sign and push reviewed `web`, `worker`, `operations` digests into the account's `classpulse/*` ECR repositories. Repositories/signing are account bootstrap prerequisites, not silently created by the template. Use the same digests for promotion. The operations target includes migration tooling; never route traffic to it.
6. In a private one-off migration task, inject only the owner URL (TLS with approved RDS CA). Run Prisma `migrate deploy`; it applies tracked SQL, including RLS roles. Then separately provision/verify nonowner login credentials: app→`app_runtime`, dispatcher→`app_dispatcher`, retention→`app_retention`, billing importer→`app_billing_importer`. Login creation/password rotation is a restricted bootstrap procedure, not web initialization. Do not use `scripts/migrate.ts` as a general production bootstrap: it is local setup tooling.
7. Set runtime secret URLs with separate logins, TLS validation and correct password encoding. Never disable certificate verification. Verify database CA trust in the actual Node/Prisma images. Run negative owner/role/BYPASSRLS tests from the deployed task identities. For GHS billing, inject a **test** Paystack key only into the isolated billing job; never into the web task.
8. Enable synthetic-only staging tasks through a reviewed change set, verify real login/MFA, module/tenant scope, provider mail/storage/version/deletion access, all report formats and failure behavior. Demonstrate restore/tombstones and operational alerts. No actual candidate data until legal/privacy gates close.
9. Resolve P6-B01–B05, P6-G01–G06 and launch discovery/terms gates. Record current source commit, approved image digests and HTTPS evidence links/approver identities in a release evidence object. Store it as the protected environment's `RELEASE_EVIDENCE_JSON`; the checked-in file remains a NO_GO template. Using an externally approved object avoids a self-referential Git commit hash. The checker validates structure and exact commit/target, not signature authenticity; approvers must verify the evidence and protected-environment configuration.
10. Configure environment variables `AWS_DEPLOY_ROLE_ARN`, `AWS_ACCOUNT_ID`, `STACK_NAME`, `CELL_PARAMETERS_PATH` (committed non-secret AWS CLI parameter array). Dispatch the workflow from the reviewed commit. It verifies account/region, then deploys a **dark** stack; it does not migrate a public workload or turn traffic on. Do not run it against an already serving cell: use a separate dark/candidate stack and reviewed cutover. Cutover/traffic promotion remains manual pending independently tested rollback and smoke evidence.
11. Repeat account/provider/restore checks in production, run the one-off migration with expand/contract review, and approve controlled task activation plus DNS/traffic cutover. Verify external HTTPS certificate/headers/auth, dedicated synthetic tenant smoke, errors/queue age and provider effects. Proceed to a closed pilot only after the release owners sign. No automatic GO is inferred from this document.

## Recovery and retention

RDS PITR retention is configured at 35 days and Redis snapshots at seven days; retained stacks/snapshots and S3 versions need a reviewed inventory, expiry and hold exception procedure. No unreviewed bucket lifecycle rule silently deletes held data. These configurations are not tested backup/restore or deletion evidence. Proposed recovery targets remain RPO ≤24h/RTO ≤8h for approved scenarios. Same-region Multi-AZ does not cover regional disaster; no cross-border backup/replication is enabled. Restore steps and measurement record are in OPERATIONS_RUNBOOK.md.
